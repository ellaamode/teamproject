금융규제통합조회 (가칭)

금융관계법령 규제정보 통합조회 서비스

정의 배경 팀 기능 데이터 아키텍처 구조 고민

1. 무엇을 만드는가?

금융규제통합조회는 입법예고, 법령개정, 법령해석, 비조치의견을 한 곳에 모아 업무 태그와 키워드로 찾아볼 수 있게 하는 서비스입니다. 금융회사 업무담당자가 스스로 최신 규제 현황을 검토하는 단계를 지원합니다.

2. 왜 필요한가?

금융회사 현업에서 기술적인 이슈를 제외하면 가장 큰 제약은 금융규제입니다. 법령의 개정과 최신 해석 사례가 여러 곳에 흩어져 있고, 금융당국이 제공하는 페이지도 찾아보기 번거롭습니다.

법령·규정의 개정, 그 해석 사례, 비조치의견은 실제 업무와 가장 밀접하게 맞닿아 있는 정보인데도, 지금은 업무담당자가 이를 스스로 파악하기 어려운 구조입니다.

3. 누가 만드는가?

양정모 양지선 이수정 김한룡 최은정

4. 어떤 기능을 제공하는가?

입법예고, 법령개정, 법령해석, 비조치의견을 한 곳에 모읍니다. 업무와 관련된 태그를 선택하면 미리 매핑해 둔 항목을 전부 모아 보여주고, 별도로 검색어를 입력하면 태그·법령과 무관하게 전체에서 찾아줍니다.

태그별 조회

업무 태그를 선택하면, 미리 매핑해 둔 입법예고·법령개정·법령해석·비조치의견을 검색어 없이 전부 모아 보여줍니다.

키워드 검색

태그·법령과 무관하게, 입력한 단어가 들어간 항목을 전체에서 찾습니다.

사례 상세보기

질의요지·회답·이유 등 원문 내용을 그대로 확인합니다.

태그·키워드 매핑

팀이 설계한 매핑표를 기준으로 항목을 자동 분류합니다.

최신 현황 갱신

버튼으로 법령해석포털의 최근 등록 사례를 갱신합니다.

분석 페이지

태그별 매칭 건수, 법령별 개정 빈도 등을 정리해 보여줍니다.

아래는 두 기능을 직접 확인할 수 있는 예시 화면입니다.

"태그로 보기"에서 "외환"을 선택하면 검색어 없이도, 외국환거래법 항목뿐 아니라 자본시장법의 "장외파생상품 외환 헤지" 조항까지 함께 나옵니다 — 태그가 법 하나에 묶여 있지 않다는 뜻입니다. 자본시장법의 "역외펀드 외환 헤지 비율" 비조치의견은 외환과 느슨하게만 관련돼 있어 이 태그엔 없고, "키워드로 찾기"에서 "외환"으로 검색해야 나옵니다. 데이터는 화면 구성을 보여주기 위한 예시입니다.

5. 어디서 가져오는가?

원천가져오는 것방식
법제처 국가법령정보 API조문, 개정이력공식 Open API
국민참여입법센터 API입법예고공식 Open API
금융규제·법령해석포털법령해석, 비조치의견REST 호출(공식 API 아님)

법제처 API와 국민참여입법센터 API는 인증키 기반의 정식 Open API입니다. 금융규제·법령해석포털은 공식 API가 없지만, 개발자도구 네트워크 탭으로 실제 요청을 확인한 결과 selectReplyCasePastReplyList.do(목록)와 LawreqDetail.do(상세)가 이미 구조화된 JSON·HTML을 반환하는 내부 엔드포인트라는 걸 확인했습니다.

화면을 다시 해석하는 크롤링 대신, 서버가 원래 반환하도록 만들어진 값을 그대로 받는 REST 호출을 택해 무료 배포 환경에서도 안정적으로 실행됩니다.

6. 서비스 아키텍처

수집한 데이터는 PostgreSQL에 원본으로 저장하고, 사전 매핑표로 태깅합니다. FastAPI가 이 데이터를 조회·검색해 API로 내려주고, React 화면이 태그·검색 결과를 보여줍니다. 프론트·백엔드·DB 모두 무료 요금제로 운영합니다.

7. 태그를 중심으로 연결됩니다

법령 조문, 입법예고, 법령해석·비조치의견이 각각 태그에 연결되고, 태그는 키워드 사전과 연결됩니다.

erDiagram
  LAWS ||--o{ TAGS : tagged
  BILLS ||--o{ TAGS : tagged
  INTERPRETATIONS ||--o{ TAGS : tagged
  TAGS ||--o{ KEYWORDS : defines

LAWS는 법령·조문, BILLS는 입법예고, INTERPRETATIONS는 법령해석·비조치의견을 뜻합니다. 태그는 스스로 상위·하위 분류를 가질 수 있고, 이 분류 기준이 되는 것이 키워드 사전입니다.

예시로 보면

"외환 송금 한도 관련 법령해석"이라는 사례 하나가 태그에 연결되는 과정입니다.

  1. 이 사례는 금융규제·법령해석포털에서 가져온 해석례라, INTERPRETATIONS에 저장됩니다.
  2. "외환" 태그의 키워드 사전(KEYWORDS)에는 외환, 외화, 외국환 세 단어가 등록돼 있습니다.
  3. 이 사례 제목·본문에 "외환"이라는 단어가 들어있으니, INTERPRETATIONS와 "외환" TAGS가 연결됩니다.
  4. 법령 조문(LAWS)이나 입법예고(BILLS)도 같은 방식으로, 각자의 텍스트에 등록된 키워드가 있으면 태그에 연결됩니다.

같은 항목이 태그 두 개에 걸리는 경우도 있습니다. 자본시장법의 "장외파생상품 외환 헤지 관련 규정 개정"은 본문에 "외환"과 "파생상품"이 함께 등장해서, "외환" 태그와 "자본시장" 태그 양쪽에 다 연결됩니다. 하나의 조문이 여러 태그를, 하나의 태그가 여러 조문을 가질 수 있는 게 바로 이런 경우 때문이고, 그래서 LAWS·BILLS·INTERPRETATIONS가 각각 TAGS와 다대다(N:M) 관계로 설계됩니다.

자본시장법 조문 하나만 화살표가 두 개입니다 — 본문에 "외환"과 "파생상품"이 함께 있어서 "외환" 태그와 "자본시장" 태그 양쪽에 다 연결되기 때문입니다. 나머지 세 항목은 "외환" 키워드 사전(외환·외화·외국환)에 걸려 "외환" 태그 하나로만 모입니다.

8. 고민중인 부분은?

법마다 표현이 조금씩 달라서(예: 외환·외화·외국환), 조문 하나하나를 사람이 읽고 태그를 붙여야 합니다. 다룰 법이 늘어날수록 이 작업량이 커지는데, 법령의 정의조항을 기준으로 1차 사전을 만들거나 LLM으로 키워드 후보를 제안받아 사람이 검토·확정하는 방식으로 작업량을 줄이는 방법을 고민하고 있습니다.

이 태그를 사용자의 편의에 맞춰 화면을 개인화할 수 있는 방법도 함께 고민하고 있습니다.

행정지도까지 함께 보여주고 싶은데, 금융위원회 행정지도와 금융감독원 행정지도가 서로 다른 사이트에 있고 수집 방식도 다릅니다. 두 기관의 데이터를 어떻게 하나의 태그 체계 안에 자연스럽게 통합할지 고민하고 있습니다.
