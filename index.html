금융규제통합조회 (가칭)

금융관계법령의 개정, 법령해석, 비조치의견을 업무 카테고리 하나로 모아서 봅니다.

컴플라이언스 부서로 넘기기 전, 업무담당자가 스스로 최신 규제 현황을 검토하고 이해하는 단계를 위한 도구입니다.

업무담당자는 규제를 세 곳에서 따로 찾는다

금융회사 업무담당자가 자신이 담당하는 업무와 관련된 규제 변화를 확인하려면, 법제처에서 조문을 찾고, 국민참여입법센터에서 입법예고를 확인하고, 금융규제·법령해석포털에서 관련 해석 사례와 비조치의견을 따로 찾아야 합니다.

세 곳 모두 법령명이나 키워드로만 검색될 뿐, "내가 담당하는 업무" 기준으로는 아무것도 모아 보여주지 않습니다. 금융규제통합조회는 금융회사의 업무담당자가 규제 변화나 비조치의견, 법령해석에 대해 더 효율적으로 접근하고 업무할 수 있도록 지원합니다.

업무 카테고리 하나로 모아 본다

업무 카테고리를 선택하면, 그 업무와 관련된 조문의 최신 개정 이력, 법령해석 사례, 비조치의견, 그리고 예정된 입법예고까지 한 화면에서 확인합니다. 카테고리 안에서 다시 키워드로 검색해 범위를 좁힐 수 있습니다.

카테고리는 시스템이 아니라 사람이 먼저 정의합니다

카테고리를 사용 중에 새로 만들거나 자동으로 분류하지 않습니다. 어떤 법령을 다룰지, 그 법령을 업무 단위로 어떻게 나눌지, 각 업무에 어떤 법정 용어가 대응하는지를 실무 지식을 바탕으로 미리 설계해 하나의 매핑표로 만들어 둡니다. 시스템은 이 매핑표를 기준으로 조문·해석·비조치의견을 자동으로 분류할 뿐입니다.

  1. 다룰 금융관계법령의 범위를 확정한다
  2. 법령의 정의조항과 업무 영역을 분석한다
  3. 업무 카테고리 트리(대분류·소분류)를 확정한다
  4. 카테고리별 키워드 사전을 작성한다

카테고리를 선택하면 한 화면에 모인다

전체를 선택하면 관련 법령을 가리지 않고 검색어가 들어간 항목을 모두 찾습니다. 특정 카테고리를 선택하면 사전에 매핑해 둔 법령의 항목만 좁혀서 봅니다.

"전체 + 외환"으로 조회하면 외국환거래법뿐 아니라 자본시장법의 외환 관련 조항까지 함께 잡힙니다. 카테고리를 "외환"으로 좁히면 외국환거래법으로 사전 매핑된 항목만 남습니다. 실제로 select와 입력창을 바꿔 눌러볼 수 있는 예시이며, 데이터는 화면 구성을 보여주기 위한 예시입니다.

세 곳의 데이터가 하나의 화면이 되기까지

구조 개요와 실현 가능성

법제처 국가법령정보 API — 정형 Open API (6주차 방식)

조문 원문과 개정이력을 가져오는 경로입니다. 사전에 발급받은 사용자 식별자(OC)와 호출 서버의 공인 IP를 API 관리 페이지에 등록해야 동작하는 인증 방식이며, target(법령 종류), query(검색어), display·page(페이지네이션) 파라미터로 목록을 조회하고, 법령ID 또는 법령마스터번호로 조문 본문을 조회합니다. 응답이 XML·JSON 형식의 정형 데이터라 6주차에서 다루는 "인증키·Pagination·파싱·정제·저장" 흐름을 그대로 적용할 수 있습니다.

국민참여입법센터 API — 정형 Open API

예정된 입법예고를 가져오는 경로입니다. 마찬가지로 인증키 기반 REST 조회이며, 법제처의 법령 식별자와 연결되는 항목을 함께 제공해 이후 실제로 공포되는 법령과 매칭할 수 있습니다.

입법예고는 개정안이 아직 확정되기 전에 의견을 받는 단계이고, 법제처 API로 가져오는 개정이력은 절차가 끝나 확정·공포된 결과입니다. 입법예고된 내용이 그대로 확정된다는 보장이 없으므로 두 데이터를 합치지 않고 별개 항목으로 저장하며, 화면에서도 예정 사항과 확정 사항을 구분해 보여줍니다.

금융규제·법령해석포털 — 크롤링이 아니라 REST 호출

이 포털은 공식 Open API를 제공하지 않고, 목록 페이지에 접속했을 때 서버가 처음 내려주는 HTML에는 사례 목록이 비어 있습니다. 여기까지만 보면 5주차가 다루는 크롤링(BeautifulSoup으로 HTML을 파싱하거나, 화면이 자바스크립트로 채워지는 경우 Playwright로 브라우저를 띄워 렌더링된 결과를 읽는 방식) 대상으로 보입니다.

그래서 실제로 브라우저 개발자도구의 네트워크 탭으로 페이지가 데이터를 어떻게 채우는지 직접 확인했습니다. 확인 결과, 목록은 selectReplyCasePastReplyList.do에 대한 POST 요청으로 채워지고 있었고, 이 요청은 jQuery DataTables 라이브러리가 표준으로 쓰는 서버사이드 파라미터(draw, start, length, columns[] 등)를 그대로 사용합니다. 응답은 전체 건수(recordsTotal)와 사례 목록(data)을 담은 JSON이며, 전체 4,361건이 등록되어 있음을 확인했습니다. 상세 화면 역시 LawreqDetail.do에 사례 고유번호(lawreqIdx)를 실어 요청하면 질의요지·회답·이유 전체가 담긴 HTML이 돌아옵니다.

즉 이 포털은 "공식 API는 없지만 화면이 내부적으로 호출하는, 이미 구조화된 데이터 엔드포인트"를 갖고 있었습니다. 크롤링 대신 이 엔드포인트를 직접 호출하는 방식을 택한 이유는 다음과 같습니다.

  1. 브라우저를 띄울 필요가 없어 무료 배포 환경(메모리 제한이 있는 서버)에서도 안정적으로 실행됩니다.
  2. 목록 응답이 정형 데이터라 파싱 규칙이 단순하고, 화면 디자인이 바뀌어도 요청 파라미터 구조가 유지되는 한 코드가 잘 깨지지 않습니다.
  3. 한 요청에 받아올 건수를 length 파라미터로 조정할 수 있어, 전체 수집에 필요한 요청 횟수를 줄일 수 있습니다. 실제 허용 상한은 수집 단계에서 확인합니다.

다만 이 엔드포인트는 공식적으로 공개·보장된 API가 아니라 웹페이지가 내부적으로 사용하는 요청이므로, 요청 간격을 두어 상대 서버에 부담을 주지 않도록 하고, 화면이 개편되면 파라미터나 엔드포인트가 바뀔 수 있다는 점은 운영 중 확인이 필요한 리스크로 남겨둡니다. 정리하면, 크롤링은 화면에 그려진 결과를 다시 해석해 데이터를 뽑아내는 방식이고 여기서 쓰는 것은 서버가 원래 반환하도록 만들어진 값을 그대로 받는 REST 호출이라는 점이 다르며, 5주차의 크롤링 기술은 이런 내부 경로를 찾지 못했을 때 쓰는 방법이라고 판단해 이번에는 적용하지 않았습니다.

저장 구조 (4주차 방식)

법령, 조문, 개정이력, 입법예고, 해석·비조치의견 사례를 각각 별도의 표로 저장하고, 사전에 만든 카테고리·키워드 매핑표를 기준으로 각 항목에 업무 카테고리를 표시합니다. 조문 하나가 여러 카테고리에 걸릴 수 있고 카테고리 하나에 여러 법령의 조문이 걸릴 수 있는 다대다 관계로 설계합니다. PostgreSQL은 원본과 매핑의 기준(source of truth)입니다.

검색 (7주차 방식)

기본적으로 OpenSearch로 검색을 처리할 예정입니다. 필요하면 카테고리별 조회는 PostgreSQL과 함께 쓰는 방식도 함께 검토합니다.

배포

프론트엔드(Vercel), 백엔드(Render), 데이터베이스(Supabase)는 무료 요금제로 운영합니다. OpenSearch만 AWS 서비스로 별도 구성하며, AWS 프리티어 정책이 계정 생성 시점에 따라 다르므로 도메인 생성 전에 적용되는 조건을 확인하고 가장 작은 단일 인스턴스 구성으로 예산을 한정합니다.

남은 리스크와 대응

  • 법제처 API는 호출 서버의 IP를 등록해야 하므로, 배포 서버가 아니라 등록해 둔 환경에서 주기적으로 수집합니다.
  • 법령해석포털의 내부 엔드포인트는 공식 API가 아니므로, 화면 개편에 따른 변경 가능성을 주기적으로 점검합니다.
  • OpenSearch는 AWS 프리티어 조건을 확인한 뒤 구성하며, 인스턴스 유형과 예산을 해당 조건에 맞게 운영합니다.
  • 카테고리·키워드 매핑표가 다루지 못하는 사례는 미분류로 남깁니다. 이는 한계가 아니라, 법률 용어 분류에는 사람의 판단이 필요하다는 전제에서 나온 설계입니다.
